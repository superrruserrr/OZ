# Migrations de base de données

Règle R9 du plan technique et exigence EX-T09 : toute migration est réversible et testée en `up` puis `down`.

## Convention

- Une migration = un dossier `packages/db/prisma/migrations/<horodatage UTC>_<nom_snake_case>/` contenant :
  - `migration.sql` : le `up`, généré par Prisma puis complété à la main si besoin ;
  - `down.sql` : le `down`, **écrit à la main et relu en revue**, qui annule exactement le `up`, dans l'ordre inverse.
- Un `down.sql` absent ou vide fait échouer `pnpm test` (`packages/db/src/migrations.test.ts`).
- Le cycle complet `up` → `down` → `up` est testé sur un PostgreSQL jetable (`packages/db/test/migrations.int.test.ts`) : après les `down`, le schéma redevient celui d'une base vierge.
- Une migration déjà appliquée n'est **jamais** modifiée : on en écrit une nouvelle.
- `down.sql` s'exécute dans la transaction de `db:rollback` : aucune instruction `BEGIN`, `COMMIT`, `ROLLBACK`, `VACUUM`…, ni `CONCURRENTLY` (refusés par le test de convention ; les corps de fonctions, chaînes et identifiants entre guillemets sont ignorés).
- Les extensions (`pgcrypto`, `pg_trgm`, `unaccent`) relèvent du provisionnement de la base (`pnpm dev:up`, Terraform au lot 0.8) : une migration peut les exiger (`CREATE EXTENSION IF NOT EXISTS`) mais son `down` ne les supprime pas, car elles peuvent lui préexister (base managée).
- L'empreinte comparée par le test couvre l'existence des schémas, tables, colonnes (type, nullabilité, défaut), contraintes, index, séquences, vues, types et énumérations, fonctions (par signature), déclencheurs, RLS et politiques. Elle ne compare pas le corps des fonctions, les libellés d'énumération, les longueurs et précisions, les paramètres de séquence, les droits ni les commentaires (DEBT D-026) : un `down.sql` qui restaure une fonction se relit en revue.
- Prisma ne sait pas exprimer RLS, partitionnement, chiffrement de colonne (`pgcrypto`) ni fonctions : ces éléments sont écrits en SQL brut dans `migration.sql`, avec leur annulation dans `down.sql` (TD-002).
- Tables et colonnes en snake_case, tables au pluriel ; modèles Prisma en PascalCase avec `@@map` / `@map` (naming_conventions.md). Clé primaire `id UUID DEFAULT oz_uuid_v7()`, horodatages en `timestamptz` (plan §5.1).

## Créer une migration

1. Modifier `packages/db/prisma/schema.prisma`.
2. Générer le SQL : `pnpm --filter @oz/db exec prisma migrate dev --create-only --name <nom>` (base de développement démarrée par `pnpm dev:up`).
3. Compléter `migration.sql` si nécessaire, écrire `down.sql`.
4. `pnpm test` : convention, cycle `up`/`down` et concordance schéma Prisma ↔ SQL.

Attention : sans `DATABASE_URL`, la CLI Prisma 7 peut sortir en succès sans rien produire (`migrate diff`). `prisma.config.ts` refuse donc toute commande `migrate`, `db` ou `studio` sans URL ; vérifier malgré tout la sortie, pas seulement le code de retour.

## Commandes

| Commande           | Effet                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `pnpm db:migrate`  | Applique les migrations en attente (`prisma migrate deploy`) ; avec `DATABASE_CA_CERT` (recette, production), à travers un relais local qui vérifie le certificat de la base (D-039) — `prisma migrate deploy` lancé directement y est refusé                                                                                                                                                                                                                                                   |
| `pnpm db:status`   | État des migrations                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| `pnpm db:rollback` | Annule la dernière migration : `down.sql` et retrait de sa ligne dans `_prisma_migrations`, en une transaction, sous le verrou de Prisma Migrate. Refusé en production sans `--confirm-production`, si une migration est en échec, ou si l'URL est ambiguë (autre schéma que `public`, paramètre `host`, `dbname`, `options`…). Les paramètres Prisma et SSL (`schema=public`, `connection_limit`, `pool_timeout`, `pgbouncer`, `sslmode`, `sslcert`…) sont acceptés. `APP_ENV` explicite exigé |

En recette et en production, une migration est testée sur une copie de la base avant application (EX-T09.3, lot 0.8).

## Socle de données (lot 1.1a)

Migration `20261027120000_socle_identite` : `users`, `user_roles`, `sessions`, `organizations`, `players`, `guardians`, `consents`, `audit_log`. Règles qu'une nouvelle table du socle doit suivre, vérifiées par `packages/db/test/socle-schema.int.test.ts` et `rls.int.test.ts` :

- **Colonnes communes** : `id` (`oz_uuid_v7()`), `created_at`, `updated_at` (tenu par le déclencheur `oz_set_updated_at`), `deleted_at` ; `created_by` / `updated_by` vers `users` sur les tables sensibles.
- **Suppression physique interdite** sur les données de personnes : déclencheurs `oz_forbid_delete` sur `DELETE` et `TRUNCATE`. Suppression logique (`deleted_at`) ou anonymisation seulement.
- **RLS activée et forcée**, refus par défaut. Le contexte utilisateur se pose par transaction avec `withUserContext(db, userId, fn)` (`@oz/db`), qui appelle `set_config('oz.user_id', …, true)` ; `oz_current_user_id()` le lit dans les politiques. Le test échoue si une table du schéma `public` n'a pas la RLS forcée (hors `_prisma_migrations`, `system_settings`, `audit_chain_state`). La RLS protège des oublis de filtre de l'application ; elle ne remplace pas les requêtes paramétrées (une injection SQL pourrait poser le contexte). Le superutilisateur local `oz` la contourne : l'API passera à un rôle applicatif au lot 1.4 (DEBT D-055).
- **Colonnes d'autorité** : sous un contexte utilisateur, `oz_guard_authority` refuse d'écrire statut de vérification, OZ ID, titulaire, tuteur, organisation de rattachement, statut de compte, dates de vérification, et toute restauration d'une ligne supprimée logiquement. L'identité certifiée l'est aussi : la date de naissance d'un joueur toujours, nom, prénom et numéro de pièce (joueur et tuteur) ainsi que la nationalité du joueur dès que le statut n'est plus `declared` ; une correction passe par le support. Ces écritures passeront par une fonction `SECURITY DEFINER` dédiée et journalisée, jamais par une connexion sans contexte (DEBT D-059). `created_at` est immuable.
- **Email** : changer d'adresse efface `email_verified_at` (`oz_reset_email_verification`), sauf si la même requête pose la vérification de la nouvelle adresse.
- **Consentement parental** : les types `guardian_*` exigent un tuteur et le mineur concerné (contrainte `consents_guardian_grantor_check`) ; un compte ne peut pas être le tuteur de son propre profil joueur (`oz_players_guard`). Sa valeur probante dépend encore de la vérification du tuteur, qui arrive avec le parcours de vérification (lot 1.3 et suivants).
- **Chiffrement colonne** : `oz_encrypt(valeur, clé)` / `oz_decrypt(bytea, clé)` (pgcrypto, AES-256) et `oz_blind_index(valeur, clé)` (HMAC-SHA-256) pour la recherche d'égalité. La clé est toujours un **paramètre lié** de la requête (`DATABASE_ENCRYPTION_KEY`, `DATABASE_BLIND_INDEX_KEY`), jamais une constante du schéma ni d'une migration. Une colonne `*_encrypted` va avec sa colonne `*_hmac` (contrainte `CHECK`). Une mauvaise clé lève une erreur, jamais un texte faux.
- **Journal d'audit** : `audit_log` partitionné par mois (`oz_audit_ensure_partitions(n)` : mois courant et n suivants, plus `audit_log_default`). Position, `prev_hash` et `hash` (SHA-256 du contenu canonique) sont calculés par le déclencheur `oz_audit_chain`, sérialisé par la ligne unique `audit_chain_state` ; un horodatage fourni par le client est refusé. `UPDATE`, `DELETE` et `TRUNCATE` (parent et chaque partition) sont refusés par déclencheur, y compris au propriétaire ; chaque partition a la RLS forcée sans politique (aucun accès direct). Le propriétaire ou un superutilisateur peut toutefois couper les déclencheurs : la chaîne rend l'altération détectable, sauf réécriture complète tant que la tête n'est pas ancrée hors de la base (DEBT D-060). L'insertion verrouille la tête de chaîne jusqu'au commit : écrire l'entrée d'audit en fin de transaction ; `oz_audit_verify_chain()` renvoie la première position en défaut, ou `NULL`. Actions au format `{domaine}.{entité}.{verbe_au_passé}`.
- **Anonymisation** (`db:anonymize`) : stratégies `encrypted:<type>` et `blind_index:<type>` (valeur synthétique rechiffrée avec les clés de la copie, jamais celles de la production), `empty_json` et `empty_json_array`. Elle coupe les déclencheurs de sa transaction (`session_replication_role = replica`, superutilisateur requis, DEBT D-054) : la chaîne d'audit d'une copie anonymisée est rompue, c'est voulu.

## Dossiers, opérations et recherche (lot 1.1b)

Migration `20261027150000_socle_dossiers` : `documents`, `kyc_cases`, `kyc_case_documents`, `imports`, `subscriptions`, `notifications`, colonne `organizations.subscription_id`, recherche sur `players`. Vérifiées par `dossiers-schema.int.test.ts`, `rls-dossiers.int.test.ts` et `search.int.test.ts` :

- **Documents** : métadonnées seulement, un sujet exactement (joueur, tuteur ou organisation). `storage_key` est une clé d'objet unique, jamais une URL ; `sha256` en hexadécimal (détection des documents recyclés) ; 50 Mo au plus ; `retention_until` obligatoire. Numéro de pièce et extraction OCR chiffrés. Sujet et contenu d'une pièce sont figés (`oz_documents_guard`) ; elle n'est lisible que par les utilisateurs liés à son sujet aujourd'hui. L'utilisateur dépose en son nom une pièce `pending` pour l'un de ses sujets ; antivirus, OCR et purge appartiennent au système (D-059).
- **Dossiers KYC** : sujet joueur ou organisation, niveau 0 à 3, contrôles en liste JSON. Une décision (`approved`, `rejected`) porte décideur, motif et horodatage. `oz_kyc_cases_guard` n'accepte que des administrateurs actifs et exige deux administrateurs distincts pour un joueur mineur ou une organisation recruteur, agence ou centre (CP-16) ; un sujet invisible (RLS) est un refus. Le sujet est figé dès la création, un dossier soumis ne revient jamais en brouillon, et une décision est définitive (seule l'expiration d'une approbation reste possible) : un nouvel examen ouvre un nouveau dossier. L'utilisateur n'ouvre qu'un brouillon, et n'y joint que des pièces de son sujet (ou du tuteur du joueur) ; aucune pièce ne s'ajoute hors brouillon.
- **Imports** : compteurs jamais supérieurs aux lignes lues ; un import `completed` a classé chaque ligne (CP-26). Un membre de l'organisation lance un import `pending` ; le traitement appartient au système.
- **Abonnements** : palier libre, `free` par défaut (paliers payants : requirements.md Q8) ; une seule souscription en cours (`trialing`, `active`, `past_due`) par organisation, par index unique partiel. `organizations.subscription_id` est une clé composite : une organisation ne pointe que sur sa propre souscription.
- **Notifications** : gabarit nommé (`kyc.case.approved`), charge limitée aux identifiants (`oz_notification_payload_ok` : objet à plat, clés `*_id`, valeurs UUID), tentatives bornées. Le destinataire lit les siennes.
- **RLS** : chaque politique s'appuie sur la RLS du sujet (un sous-select sur `players` ne rend que les joueurs visibles). Tout membre d'une organisation, quel que soit son rôle, y dépose et lit des pièces : la matrice des rôles arrive au lot 1.4 (DEBT D-061).
- **Recherche** (EX-101 n° 6) : `oz_unaccent(text)` (dictionnaire explicite, `IMMUTABLE`) ; `players.search_vector` générée par `oz_player_search_document` (nom, prénom, ville, poste) avec index GIN ; index trigrammes sur `lower(oz_unaccent(nom))` et prénom pour la recherche floue (`%`). Les libellés de `player_position` ne doivent jamais être renommés : la fonction est déclarée `IMMUTABLE`. Prisma ne représente pas les index sur expression ni l'index unique partiel : ils vivent dans la migration seulement.
- **Restauration** : `pg_dump` pose un `search_path` vide. Toute fonction qui cite une table ou une autre fonction a donc un `search_path` fixe (`SET search_path = public, pg_temp`) ou des noms qualifiés ; la migration 1.1b l'applique aussi aux fonctions du lot 1.1a.
- **Diagramme** : `docs/data/er.md`, généré par `pnpm --filter @oz/db db:er` sur une base migrée ; `er-diagram.int.test.ts` échoue s'il n'est plus à jour.
- **Seeds** : `pnpm db:seed` crée 500 joueurs (un tiers de mineurs, chacun avec tuteur et consentement parental), 30 organisations et deux comptes par rôle, dans une transaction marquée par le réglage `seed.profiles` (idempotence). Sans clés de chiffrement, les colonnes chiffrées restent vides.

## Registre des OZ ID (lot 1.2)

Migration `20261028090000_registre_oz_id`, vérifiée par `oz-id-registry.int.test.ts` :

- **Calcul en base** : `oz_ozid_compose(pays, année, aléatoire)` et `oz_ozid_is_valid(oz_id)` reprennent l'alphabet, la table de Damm et l'ordre des valeurs de `packages/core` (ADR-007, section Calcul) ; un test croise les deux implémentations sur 10 000 OZ ID et leurs altérations. La table est figée à vie, en base comme dans le code.
- **Registre** : `oz_id_registry` (OZ ID, joueur, date d'émission), contrôle de Damm vérifié par `CHECK`. Aucune ligne n'est modifiée, supprimée ni vidée ; la ligne du joueur n'est jamais supprimée non plus : après suppression logique et anonymisation, l'OZ ID reste pris (CP-03). `players (oz_id, id)` référence `oz_id_registry (oz_id, player_id)` : un joueur ne porte que l'OZ ID réservé pour lui.
- **Émission** : `oz_issue_oz_id(joueur, partie aléatoire)`, `SECURITY DEFINER`, premier chemin privilégié (D-059). L'appelant (titulaire, tuteur actif, membre de l'organisation de rattachement ou administrateur) ne fournit que la partie aléatoire ; la base fixe le pays de rattachement et l'année d'émission UTC, calcule le contrôle, réserve (`ON CONFLICT DO NOTHING`), pose l'OZ ID et journalise `player.oz_id.issued`. Elle renvoie `NULL` si la partie aléatoire est déjà prise : l'appelant tire à nouveau.
- **Chemin privilégié** : `oz_privileged()` est vrai à l'intérieur d'une fonction `SECURITY DEFINER` dont le propriétaire n'est pas un rôle que la session peut endosser (un `SET ROLE` ne compte jamais, testé), ou quand le rôle courant est superutilisateur. `oz_guard_authority` le laisse passer ; les politiques `players_privileged` et `oz_id_registry_privileged` ouvrent la RLS forcée au seul propriétaire en cours d'exécution d'une telle fonction (testé avec un propriétaire sans privilège de superutilisateur, comme en recette). Toute nouvelle fonction `SECURITY DEFINER` reçoit donc cet accès : chacune contrôle son appelant et journalise (D-059).
- **Pays figé** : une fois l'OZ ID émis, `players.country` ne change plus (`oz_players_freeze_country`).
- **Partie aléatoire** : toujours tirée par le serveur (`issueOzId`, `crypto.getRandomValues`), jamais reçue d'un client, sinon un OZ ID « choisi » devient possible.
- **Charge** : `oz-id-load.int.test.ts` (CI) émet 10 000 OZ ID sur 20 connexions sans doublon ; le million en base se lance à la main (`pnpm --filter @oz/db test:load`). Mesure du 2026-10-27 (poste de développement, PostgreSQL 16 en conteneur, 20 connexions) : 1 000 000 d'OZ ID émis par `oz_issue_oz_id` dans un même couple (pays, année), aucun doublon ni OZ ID invalide, en 17 minutes environ ; le nombre de reprises n'a pas été relevé lors de cette exécution.
